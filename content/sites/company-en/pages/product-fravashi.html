Fravashi

A self-hosted studio where AI coding agents work on your software inside one desktop window, connected to the repository, tracker and wiki you already use, with a person approving what they change.

Why it exists

Teams that adopt AI coding agents easily lose control and context: work items, documentation and code live in three separate tools, and agents change code with nobody reviewing each step. Fravashi keeps the work and the knowledge together as one linked whole, so an agent takes its context from there, and a person directs and approves the work along the way.

It is for software teams and companies who want AI agents, but on their own machines and under their own review.

Spec-driven development

Fravashi is built for spec-driven development: work moves from a specification through a plan and a build to verification against test scenarios, and a person directs it and decides along the way. A work item and the wiki pages that specify it are linked, so an agent takes the work and the knowledge it needs from one place.

In Fravashi this is enforced, not a convention an agent may ignore. An agent can read, search and discuss at any time, but before it changes a file or runs a command, its session must be linked to a work item and a plan. If there is none, the studio refuses the change and tells the agent why, and the agent helps you write them; a typo costs one confirmed step, not a conversation. A file edit outside a declared scope or past a change budget is refused.

What it does

  • An agent session in the studio

    In a conversation, Claude Code works on a contained copy of the repository, and its changes sync back to your folder. Each Claude Code process starts from an allowlist of named variables, so the studio's bridge token, window token and integrity key do not reach it. It holds what it is given on purpose: a short-lived broker token instead of the key when your organisation's broker carries it, otherwise your own API key or sign-in token, plus any variables you added to the project, including secrets. Proxy settings are passed on as they are. It can ask you real questions, and file changes ask a person first, unless you trust edits for that folder (even then, an agent's edits to hidden files and to the repository's git configuration still ask); commands always ask, and so does any file outside the copy, apart from reading the session's own memory and tool results.

  • A second review

    By default, every commit an agent makes is reviewed by a second agent before a person is asked to approve it. A failed review is refused; a review that gives no verdict still reaches the person, who is told.

  • Tracker and wiki

    A built-in tracker and wiki, two views of one linked graph, that agents work through the studio's own tools and that connect to Azure DevOps Boards and Jira for work, and Confluence for documentation; changes go out when you send them, never silently.

  • Code and pull requests

    Git and pull requests on GitHub, Azure DevOps and Forgejo, with a code editor in the studio.

  • Autopilot

    Marked work items are built unattended, each in its own working copy, and the result is judged against the item. Routine approvals are decided by rules and a judge; the rest come to you.

  • Scenarios and evidence

    A work item carries test scenarios: ordered steps, each a command the studio runs or a step a person checks. Running one records evidence on the item, and only all steps green is a pass. A step a person checks is recorded as not run, so a run with one ends as partial.

  • Designs

    A design editor, with approval per work item.

  • Several sessions at once

    Several agent sessions can run at once, but only one conversation edits a folder at a time. When an Autopilot run may use more than one session, each item gets its own git worktree; the limit you set counts sessions per repository.

  • Import an existing project

    Fravashi surveys a folder you choose and proposes work items and wiki documents from it. Before the survey runs, it shows who receives what, which files, what is kept back and what it costs; afterwards you review what it found, answer what it could not tell, and import into the board and the wiki. Importing again brings in what is new and what changed, but leaves alone anything you have edited in Fravashi since.

Availability

Fravashi is in development and not yet generally available. It runs as a Windows desktop application that hosts the studio in a Linux container on your own machine.

To follow it or to try it with your team, ask through the contact form. Using it needs a Nova Globen account, and accounts are given on request.
